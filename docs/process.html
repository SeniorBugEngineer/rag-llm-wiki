這一頁依照繳交要求，依序說明 Wiki、簡報、loop／graph 設計、實際執行紀錄與反思。本頁的執行紀錄表由腳本直接從 log.md 產生，沒有人工改寫。

1LLM Wiki 主題與簡介

主題是 RAG（Retrieval-Augmented Generation，檢索增強生成）：讓 LLM 回答前先從外部資料中找出相關段落，再依據這些段落生成答案。

Wiki 以「先討論、後生成」的方式建立：主題、交付形式、書單、graph 實作方式都先逐項討論確認，寫成設計規格後才開始 ingest。內容共 8 篇資料、21 頁（8 頁資料摘要 + 13 頁概念），每個概念頁的每項說法都標註來源頁。

4loop／graph 設計

問題回答
哪些步驟會重複執行？Wiki 迴圈每篇資料跑一次（8 次）；C1 失敗就重抓（換 URL 或格式）；C2／C3／C4 失敗就「修正 → 重跑」，直到通過，而且每一輪都寫入 log。
哪些地方需要檢查或重新生成？C1 來源核實（標題、作者、年份）→ C2 Wiki 結構（欄位、連結、孤立頁）→ C3 大綱每個論點都有出處 → C4 每張投影片都有出處 → C5 瀏覽器實測與新手通讀。v2 再加上 C0 可抓取預檢，以及 C2+／C3+／C4+ 數字對應。重新生成時只重做失敗的頁面或投影片。
為什麼這樣設計？(1) 出處貫穿全程：source id → Wiki frontmatter → 大綱 src: → 投影片 data-src，任何一段斷掉，腳本都能抓到，保證簡報對應 Wiki。(2) 局部重生，避免整份重寫又引入新錯誤。(3) 檢查是程式，結果可以重跑、可以驗證，log 才可信。

完整規格見 WORKFLOW.md。檢查腳本：check_wiki.py（C2）、check_slides.py（C3／C4）、check_claims.py（v2 的 C2+／C3+／C4+），共 22 個單元測試。

最常出錯的是 C1「取得資料」（3 次）。三次失敗都跟內容無關，都是「格式抓不到」：抓網頁的工具不肯回傳 abstract 原文、http 呼叫被轉址後拿到 0 bytes、PDF 只得到二進位。另外，計畫寫的後備順序是 abs → html → pdf，我實際執行時卻先試了 PDF，多繞了一輪。

最危險的是語意錯誤（2 次）。C2、C3 都顯示 PASS，但概念頁的引用歸屬寫錯了，大綱裡也有一個論點引用了不含該內容的頁面。v1 的檢查只驗證「出處檔案存在」，驗不到「出處是否真的支持這句話」。這兩個錯誤都是我在正式檢查之外，臨時多加檢查才抓到的。

發現問題後，把檢查往前移到哪一步？

  • C1 → 討論書單時：新增 C0「可抓取預檢」，選書時就確認每篇都能用 arXiv API 或 HTML 取得文字，並把抓取順序固定為 API → HTML、不抓 PDF。
  • 語意檢查 → 撰寫 Wiki 當下：把臨時腳本正式化為 check_claims.py（先寫測試）。Wiki 頁的每個數字都必須出現在它引用的 raw 原文中；大綱和投影片的數字也必須出現在它們引用的 Wiki 頁中。錯誤越早抓，要回頭重做的步驟越少。

有沒有因此修改 workflow／graph？為什麼？

有，從 v1 改成 v2（見上方第 4 節的圖）。v2 第一次執行時，C2+ 抓出 3 處單位換算（例如原文 21M 寫成「2,100 萬」），C4+ 抓出第 8 張的示意向量。這些都是刻意的改寫，所以改用 <!-- num-ok --> 明確標註後放行，讓「刻意改寫」和「打錯字」可以被區分，也留下可審查的痕跡。

還有一件意外的收穫：C5 第一次看起來「手機版溢出」，量測後才發現是 headless 瀏覽器的最小視窗寬度約 496px 所造成的假象。所以 v2 的 C5 改用 400px iframe 實測。檢查工具本身也會出錯，判定失敗前要先確認是頁面的問題，還是工具的問題。

v2 的限制：check_claims 只保證「數字有出處」，像「A 優於 B」這類文字主張，仍需要人工通讀。
